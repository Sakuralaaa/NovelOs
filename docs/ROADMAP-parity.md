# 对齐并反超炼字工坊：功能路线图（parity roadmap）

> 起草：2026-11-17。基线：NovelOS **v0.11.1**（`backend/app/__init__.py`、`frontend/package.json`；HEAD `a9bbf4c`，v0.11.2 侧栏子条目布局在本地进行中）。
> 对照对象：炼字工坊（lianzigongfang.com，v2.7.85）免费账号 2026-11-17 实测，覆盖 我的小说 / 我的剧本 / 我的漫剧 / 实用短篇 / 同人创作 / 创作工具 / 数据中心。同人生成阶段在对方订阅墙后，未能实测。
> 目标：对方有的我们都要有，并且做得更好。
> 规则：只借鉴流程与交互，不复制对方文案、提示词原文或代码；NovelOS 里新增的提示词、模板、卡片文案全部自写。本文不涉及申报/合规类文案。

## 一、结论先说

1. **对照统计**：拆出 146 个功能点（不含灵石/会员/签到等不适用项）：**已有且更强 56 项、已有但较弱 45 项、缺失 45 项**。
2. **强项集中在长篇写作的「底账 + 程序校验」**：事实账本、伏笔账本、场景状态账本、节奏体检、证据式审稿、数值一致性 lint、断点续跑、多版本择优、写前成本预估、风向标日报、仿写相似自检、同人 OOC 与原文重合检查。炼字在这些环节主要靠提示词输出大段文本。
3. **缺口集中在四块**：① 整条「剧本 / 漫剧 / 实用短篇」产品线；② 作品数据进出（导入已有作品、导入导出、回收站、选章导出、一键发布）；③ 写作台的小工具（AI 章名、脑洞抽卡、神评、查找替换、听书、手机预览、笔记、知识库）；④ 提示词工作台（版本、参数化表单、自建工具）和 @ 变量体系。
4. **反超的三个最大杠杆**（详见第五节）：
   - **全开放 + 成本透明**：自托管、自带模型（BYOK），把炼字锁在订阅墙后的能力（导入导出、批量消痕、导出章节、多书熔炉、同人创作、高级模型、一键发布）全部默认可用；每次生成前按自己模型的单价估出人民币金额，有预算上限，结算可逐条核对。
   - **底账驱动的一致性，并把它延伸到导入的旧书、同人、剧本和漫剧**：同一份设定卡 / 事实账本 / 伏笔账本喂给所有产线，让「换皮、改编、续写」都不崩人设、不丢伏笔。
   - **生成不覆盖、失败必可见**：所有产出进生成档案并版本化，追问生成新版本、旧版保留；失败一定有记录、原因和重试入口。这直接对着炼字实测暴露的「追问覆盖结果不提示」「漫剧生成无产出无报错无记录」「两套设置不同步」。

### E0 同人：三步立项 + 原创主角（P0 为 E0a，P1 为 E0b）

覆盖：Q1、Q2、Q5、Q6、Q7、Q9、Q14（E0a）；Q10、Q11、Q12、Q13（E0b）。延续 `docs/ROADMAP-fanfic.md` 的 P0/P1/P2。

比炼字好在哪：
- 炼字的「穿越空降」只是一段写进想法框的模板文字；我们把原创主角做成**结构化角色卡**（来历类型、能力与代价、初始关系、切入时间点），并且有**世界规则一致性检查**兜底，原创主角越过原著力量体系上限、和时间线冲突会被点名。
- 炼字的原著档案按条付费解锁（整本 26.9 万灵石）；我们的原著资料由作者自建或联网取材，全部可看可改，没有解锁环节。
- 炼字创建同人作品要订阅；我们全部可用。
- 「融合二创检查」炼字只是一个被订阅墙挡住的按钮；我们给出可执行的冲突清单和统一规则，并能写进设定库。

实现要点：
- **E0a 三步立项**（`frontend/src/pages/FanficNew.tsx` 改为步骤条，配合 v0.11.2 侧栏子条目）：① 选原著（主原著 + ≤9 部融合原著卡片网格）② 创作想法（方向 chip → 带空位的模板；主角来源；切入点）③ 确认设置（遵循度、视角 5 选、章幅 2000/3000/5000/8000、总章数 + 每卷章数 → 自动算卷数与预计总字数、是否完本模式）。想法草稿存 localStorage，可导出/导入 JSON。
- **方向空位**：`services/fanfic_directions.py` 每个方向增加 `slots: [{key, label, placeholder, optional}]`，前端渲染成小表单，同时拼成想法文本；空位一律「可不填」，生成时让 planner 补全并标出哪些是 AI 补的。顺带补齐方向：多本穿越、反向穿越、角色复活、烂尾续写（文案自写）。
- **原创主角**：`Book.fanfic.protagonist = {source: "canon"|"oc", oc_type: "transmigrator"|"native"|"soul_swap", card_id, entry_event}`；原创角色写进设定库 `Card.data.origin = "oc"`；`POST /api/books/{id}/fanfic/oc/generate`（Job，planner）按原著设定卡补全身份、能力、代价与上限、性格与说话方式、想接触的原著人物、初始关系；`entry_event` 取原著资料时间线的某个节点。
- **上下文**：`services/context.py` 的同人块加入原创主角卡 + 切入点前后各 N 个原著事件摘要；魂穿时 OOC 检查改为「身体身份层」比对。
- **世界规则检查**：`POST /chapters/{id}/ooc-check` 结果新增 `world_rule` 类问题：原创角色能力/成长与原著力量体系上限、时间线冲突（复用 `prompts/fanfic_ooc.md`，加一段规则，自写）。
- **E0b 原著资料增强**：`fanfic_source` 人物增加 `stages[{period, timeline_ref, power, identity, relations}]`（多阶段状态）；切入点选定后上下文只取对应阶段；资料详情页加「关系索引」视图（由 relations 汇总，可按关系类型筛选）、角色按势力分组；`POST /api/books/{id}/fanfic/fusion-check`（Job）比较多部原著的力量体系、世界规则、时间线，输出冲突清单 + 建议统一规则，可一键写进设定库「世界观」卡。

工作量：E0a **L**（步骤条 M + 原创主角与检查 M）；E0b **M**。

### E1 导入已有作品 + 接管旧书（P0）

覆盖：B4、E6。

比炼字好在哪：炼字「导入文件」要付费，导入后只是一堆章节文本。我们免费导入，并且能**接管**：从已写正文反推设定卡、事实账本、伏笔账本和章细纲，之后续写直接接上底账，一致性检查对旧章同样生效。

实现要点：
- 新服务 `services/import_book.py`：复用 `services/imitate_txt.py` 的编码识别（utf-8 / gb18030 / BOM）与切章规则，去掉前 10 章限制，增加「第X卷」识别；支持 TXT / MD / DOCX（新依赖 `python-docx`）/ 粘贴。
- `POST /api/books/import`（multipart 或 JSON，同步解析）→ 返回预览：书名猜测、卷章列表、每章字数、疑似断章/重复章/空章（复用 `services/book_check.py` 规则层）；`POST /api/books/import/commit` 建书写章（状态直接为 committed，正文入库）。
- 接管任务 `POST /api/books/{id}/adopt`（Job `book_adopt`，参数 `from/to/steps=[summary, bible, ledger, outline]`）：逐章生成摘要（`prompts/summary.md`）→ 汇总反推设定卡（走 `bible/propose` 的冲突审阅）→ 回填事实账本与伏笔账本（复用 `services/changes.py` 的 ChangeSet 结构，按章入账）→ 反推章细纲并补上节奏标注（顺带完成 `CONTENT_OPTIMIZATION.md` 未实现项第 2 条「节奏标注回填」）。每章写断点（`job_checkpoint`），可暂停、续跑。
- 大纲导入（E6）：`POST /api/books/{id}/outline/import`（Job）粘贴已有大纲/卷纲/章纲文本 → planner 结构化成节点 → 预览 → `outline/apply` 采纳。
- 前端：书架页「导入作品」对话框（文件/粘贴两种）+ 预览表；概览页「接管进度」卡。

工作量：**M**（导入与切章 S，接管任务 M，大纲导入 S）。

### E2 生成档案 + 成本透明（P0）

覆盖：K1、K2、E5，并为 P2、短篇、剧本、漫剧打底。

比炼字好在哪：
- 炼字追问会**覆盖**结果工作区且不提示（实测 4,369 字消痕结果被 59 字覆盖）；我们每次生成、追问、续写都是新版本，旧版保留，可并排对比、任选采纳。
- 炼字只有黄金开篇弹窗有预估，其他操作事后结算；我们所有生成按钮已有 token 预估（`CostButton`），再加上**按自己模型单价折算的人民币金额**和**预算上限**。
- 炼字漫剧生图失败「无产出、无报错、无记录」；我们规定失败一定写档案（原因、可重试），空结果（0 张图、0 字）按失败处理。
- 炼字短篇请求 12,000 字实出 5,017 字不提示；我们对有目标字数的生成比对实际字数，不足时提示并给「续写补足」。

实现要点：
- 新表 `generation`：`id, book_id, chapter_id, kind, tool, prompt_name, prompt_version, parent_id, status(ok/failed/empty), error, output(Text), output_words, target_words, in_tokens, out_tokens, cost_cny, model, ms, starred, created_at`。在 `llm/gateway.py` 的 chat / chat_json / images 出口统一落库，替代 `llm/trace.py` 的内存记录（完整提示词是否落盘仍受 `NOVELOS_LLM_TRACE` 控制）。
- 模型单价：`Channel` 新增 `prices: {model: {in, out}}`（元 / 百万 token，可手填）；`services/estimate.py` 返回 `cost_cny`；结算按 `llm_usage` 实际 token 计算。
- 预算：设置里加每日上限与单书上限（KV），超出前拦截并说明已用多少、还差多少；mock 模式不计费。
- 接口：`GET /api/generations?book_id&kind&q&from&to&starred`、`GET/PATCH/DELETE /api/generations/{id}`、`POST /api/generations/{id}/followup`（Job，产出 parent_id 指向原条的新版本）。
- 前端：`pages/History.tsx`（类型筛选、搜索、日期、查看、复制、收藏、追问、应用到…）+ 通用 `VersionStrip` 组件（v1/v2/v3 切换 + 对比），大纲节点、改写稿、短篇等生成面板复用。

工作量：**M**。

### E4 章节工具补齐 + 写作笔记（P0）

覆盖：F10、F11、F13、F14、F18、F19、F20、G6、J2。

比炼字好在哪（逐项）：
- **AI 章名**：单章 5–9 个候选 + 批量区间；按长度、钩子词、与相邻章不重复打分，并对照章细纲 `must_avoid`，**不剧透本章反转**。

- **神评**：4–6 个番茄读者画像出段评，每条评论锚定原句（复用审稿引文校验，引不出原句丢弃），汇总「弃读点」，一键转为改写要求。炼字神评无锚定、无后续动作。
- **章内拆书**：拆书来源增加「本书某章」，产出与本章细纲的执行度对照。
- **查找替换**：正文 / 设定 / 大纲 / 笔记四个范围，支持正则；先列出全部命中预览，执行前存快照、章节进 history，可整体撤回。
- **高频词面板**：2–4 字 n-gram 统计（排除设定库人名），与 lint 的强化词/重复短语联动，一键把选中词交给人味修整。
- **手机预览**：按番茄阅读器版式渲染，标出首屏能看到多少字、第一个冲突是否落在首屏（复用 lint 开篇检测）。
- **写作笔记**：目录 + 笔记，`@笔记名` 可引用，Markdown 导入导出，全部免费（炼字笔记导入导出为订阅专享）。

实现要点：

- **E16b 漫剧流水线**：表 `comic_project`（画风、画幅、平台、单镜时长、每集时长、模型）、`asset(id, project_id, kind: character|scene|prop, card_id, name, desc, main_image, state_images JSON)`、`shot(id, project_id, episode, order, group, duration_s, prompt, dialogue JSON[{asset_id, text}], board_image, video, status, error)`；脚本解析 Job 输出「镜头/角色/场景/物品」变更 → 复用 `ConflictReview` 的待确认模式 → 同步资产；新路由 `Routing.video`（OpenAI 兼容或可配置 HTTP 适配器）；每个镜头一个 Job，批量渲染、仅选未生成、清理失败；导出 zip（视频 / 分镜图 / 字幕 SRT / 镜头表 CSV），缺视频用分镜图或黑屏补齐；剪映草稿导出需先调研其草稿 JSON 格式（列为风险，先做 zip）。
- **画布**：选用 MIT 协议的 Excalidraw；tldraw 的许可需核实后再决定。
- 工作量：E16b **XL**。

### E17 实用写作工具（P3）

覆盖：P4。

## 五、反超的三个最大杠杆

1. **全开放 + 成本透明（E2、E6、E8、E14 及全部订阅墙项）**
   炼字的商业模式决定了关键能力在订阅墙后（导入文件、AI 消痕不限次、批量消痕、导出章节、一键发布、设定/大纲/作品信息导入导出、多书熔炉、AI 书测、同人创作、高级模型）。NovelOS 自托管 + BYOK，这些全部默认开放；再把「生成前按自己单价估金额、预算上限、逐条结算」做好，作者可以用更便宜的模型跑批量工序、用更好的模型写关键章，成本始终可控。这是最容易让付费用户迁移过来的一点。
2. **底账驱动的一致性，覆盖所有产线（E1、E0、E11、E13、E16）**
   炼字的长篇记忆主要靠 @变量把文本拼进提示词；NovelOS 已有事实账本、伏笔账本、场景状态、数值 lint、证据式审稿、OOC。路线图把这层延伸到：导入的旧书（接管后续写不崩）、同人原创主角（世界规则检查）、角色灵魂卡（能打分验证）、剧本改编（复用设定与账本）、漫剧资产（角色卡即资产）。百章以后的一致性是网文作者最痛的点，也是对方最难追的点。
3. **生成不覆盖、失败必可见、过程可审查（E2、E5、E7）**
   炼字实测的三个坑——追问覆盖结果不提示、漫剧生成无产出无报错无记录、两处设置状态不同步——都是「生成过程不可审查」。NovelOS 本来就是「先预览后采纳、旧版本可撤回」的设计，再加上统一的生成档案、提示词版本化与 A/B、上下文构成可视化、条目锁定，作者能看清每一次 AI 改了什么、用了哪个提示词、花了多少钱、为什么失败。

## 七、实施约束（沿用仓库既有原则）

- 只借流程与交互，不复制炼字文案、提示词原文、模板文案和代码；内置卡库、方向模板、提示词全部自写。
- 原文不入库：导入他人作品（拆书、熔炉、同人、蒸馏）只存结构化产物与 8 字指纹；作者自己的作品导入（E1）正常入库。
- 先预览后采纳、写前存旧版本、删除类永远确认；新增写库路径都要接冲突审阅或版本栈。
- 所有新表、新列走现有自动迁移；旧书、旧数据不受影响；mock 模式全流程可跑。
- 每个 Epic 交付：pytest 用例、`frontend/scripts/screenshot.mjs` 截图、CHANGELOG 条目、`docs/API_CONTRACT.md` 增补。
