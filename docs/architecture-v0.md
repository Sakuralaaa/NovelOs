# 架构方案 v0（2026-11-12，待用户确认）

项目代号暂定：NovelOS（可改）。协议建议 Apache-2.0。不复制 AGPL/GPL/无协议项目的代码，只借思路；MIT/Apache 规则文本可复用并保留署名。

## 设计原则
1. 确定性编排：主循环是代码写的状态机，不调 LLM；只有需要判断的节点才调模型（ainovel-cli）。
2. 唯一底账：所有事实存在一份结构化底账里，摘要、向量、图谱、上下文卡都是能重建的派生视图（oh-story、webnovel-writer、inkos）。
3. 先写对再改：人味靠规划层预防和正向写作规则，事后改写只做定点修补，确定性 lint 放最后。
4. 评审只认证据：审稿必须引原句，分数由程序计算（wfcz10086、webnovel-writer）。
5. 人在关键闸门：选 idea、定大纲、发布前三处必须人工确认，其余可全自动。

## 流水线（10 个模块）
1. 热点雷达：番茄 App 榜单接口为主（匿名、明文），Web 榜单页为备用（需解码私用区字体）。每天一次快照，算排名升降、题材热度、在读/字数比。只取公开字段，可一键关闭。
2. 选题：热点 → 题材矩阵 → 3 张 idea 卡（卖点、爽点类型、差异化、仿写适合度评分），读者小组预评（MiroFish/autonovel 思路，轻量 4–6 个画像）。
3. 设定库：schema-first 卡片（世界观、力量体系、势力、人物、物品、地点），分“作者真相”和“读者已知”两条线，人物带 known_by 知识边界。
4. 规划：总纲 → 卷 → 弧 → 章细纲，滚动规划（只展开当前两卷/弧），黄金三章、排卷纲四问、伏笔池（埋设/推进/回收）。没细纲不许写正文。
5. 正文：每章先组 Context Pack（固定资料在前、动态状态在后，提高缓存命中），加载正向写作规则 + 同题材范文 few-shot + 钩子规则（主角 300 字内出场、1000 字内钩子、章尾钩子），按字数预算分段生成。
6. 审稿与提交链：正文必须附 CHANGES 变更声明（新人物、状态变化、伏笔动作）。依次过：schema 校验 → ID 引用 → 一致性 → 未登记实体 → 出场守卫 → 证据式多维审稿（爽点、节奏、OOC、连贯、追读力）。不过就打回定点重写，过了原子入账。
7. 人味层：确定性 lint（全书 n-gram 复用、句式口癖、禁用表、AI 腔词）→ LLM 定点重写每章 2–5 处 → 双轴打分（质量 × AI 味）。阈值用番茄同题材人写头部作品校准 P10–P90。
8. 包装：书名、简介、标签按番茄建书字段生成；封面 = 题材视觉模板（参考 shuixian 提示词结构）→ 用户的 OpenAI 兼容 images 接口出 4 张候选 → 本地叠加书名排版。
9. 发布：默认生成“发布包”（建书资料、分章 txt、封面、AI 申报提示），人工在作者后台上架并如实勾选 AI 申报。可选“半自动”插件：Playwright 只填草稿不点发布，默认关闭，带风险提示。
10. 复盘（v0.3）：读取自己作品的公开数据，回写到题材画像和选题评分（Easel 思路）。

## 长篇记忆
- 底账（SQLite）：entities、facts（带生效章节区间）、relations、timeline、foreshadow_ledger、chapter_commits。
- 派生：章/弧/卷三层冻结式摘要；向量索引（sqlite-vec 或 LanceDB）；关系图。全部可由底账重建。
- 回读推荐：按伏笔、出场、关系、状态挑旧章片段，而不是盲目塞上下文。
- Agent 会话内用分层压缩（billion-context 思路）。

## 多 agent 分工
Scout（雷达/选题）、Architect（设定/大纲）、Planner（细纲）、Writer、Continuity Checker（程序为主）、Editors（节奏/爽点/人物各一，证据式）、Adversarial Cutter（砍 500 字）、Reader Panel、Humanizer、Packager。Arbiter 只在冲突时单次裁定。

## 写作技能层
方法论做成可插拔技能包（兼容 SKILL.md 格式），按流程环节挂载：选题、设定、大纲、正文、审稿、去 AI 味、包装。按环节的规则模块与来源见 work/skills-fusion-report.md 第三部分。MIT/Apache/CC BY 文本可复用署名；无协议/GPL 来源（Tomsawyerhu、fanqie-novel-skill、fanqie-short-story、jiaw-Zh、webnovel-writer）只借思路自写。orange2ai/renwei-writing 有商用限制，不用。

## 模型接入
统一 OpenAI 兼容客户端，多渠道（base_url + key + 模型），按任务路由：规划/正文/审稿/嵌入/生图各配一个，失败自动切换，记录 token 与成本。可直接对接 new-api、gpt-load 这类网关。

## 技术栈建议
- 方案 A（推荐）：Python FastAPI + SQLModel + SQLite(+sqlite-vec) + 任务队列（arq 或内置），前端 React + Vite + TS，Docker 一键自托管；以后可用 Tauri 包成桌面端。理由：爬虫、字体解码、AI 生态都在 Python，参考项目多数同栈。
- 方案 B：TypeScript 全栈（Node/Hono + React），一种语言，Electron/Tauri 更顺。

## MVP（v0.1）
雷达（App 榜单）→ 选题 → 设定 → 大纲/细纲 → 正文 → 提交链 + 审稿 → 人味 lint → 简介/封面 → 导出发布包。单用户、Web 自托管，验收标准：一本书连续跑完前 30 章无设定冲突。

## 路线
- v0.2：读者模拟小组、拆书/仿写、伏笔可视化、阈值校准语料集、技能市场。
- v0.3：桌面端、半自动发布插件、数据复盘回流、短剧改编。

## 风险
- 爬榜（中）：用户协议 1.3/4.1.1/4.1.3 禁止爬虫与自动化接入；robots.txt 不拦。对策：每日一次、只取公开字段、仅内部选题、可关闭。
- 自动发布（高）：无官方 API，协议禁止自动化工具；平台限制发文量，账号实名绑定。对策：默认人工上架。
- AI 内容：番茄要求显著标识并在发布时如实勾选 AI 申报；2026 年多轮整治批量 AI 水文（具体账号数、拒签数仅见媒体转述，未核实原始公告）；国家《人工智能生成合成内容标识办法》对生成内容有标识要求（具体条款未在本方案中核对原文）。对策：系统内置申报提醒，强调人工改写把关。
